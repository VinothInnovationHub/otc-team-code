Network reality: three deployments, one constant

All three were tried on the current VNet/subnet. Each hit the same control — Azure's network layer, not application code — at a different point in the request path.

SCENARIO 1
Adaptive Card + paperclip → App Service
Inbound OK · outbound blocked
SCENARIO 2
Teams WebView / Tab → App Service
Inbound blocked — DNS
SCENARIO 3
Hosted Agent via REST API (Foundry)
Upload works · download blocked
Statement

All three scenarios fail at the same layer: Azure's network controls (NSG, firewall, private DNS) on this VNet/subnet — not application code, not the choice of App Service vs. a hosted agent vs. any future compute. Every Azure compute resource placed in this environment is controlled the same way, inbound and outbound, until its specific IP ranges/domains are explicitly allow-listed by network/security. There is no deployment option that avoids this.

The only path that does not depend on a network change: upload and download move directly between the browser and Blob Storage's own public endpoint, authorized by a single-file SAS link that expires in 5–10 minutes.

This still requires explicit Security approval — it is a public-internet-reachable endpoint, even though access is scoped to one file and time-limited.

ONLY ALTERNATIVE
Direct Blob Storage upload / download — short-lived SAS
Needs Security sign-off, not Network

Recommended — three concrete actions

01
Allow SharePoint 443 (outbound rule)

Action: add one outbound NSG/firewall allow rule on the App Service's egress subnet — destination *.sharepoint.com / graph.microsoft.com, port 443 (the SharePointOnline service tag covers both).

Fixes: Scenario 1's blocked attachment fetch and Scenario 3's blocked download — completes the current Adaptive Card + paperclip design end-to-end, since inbound already works today.

Owner: Network / Firewall teamEffort: one rule change
02
Blob Storage direct upload/download

Action: bot issues a single-file SAS token, 5–10 min expiry; browser uploads/downloads straight against Blob Storage's public endpoint.

Fixes: removes the SharePoint/OneDrive dependency entirely — works regardless of any NSG or firewall state, no network ticket required.

Owner: App team — code onlyNeeds: Security sign-off
03
Resolve DNS for the WebView/Tab path

Action: publish a public DNS record for the tab's hostname pointing at App Gateway's existing public frontend IP, instead of relying only on the private DNS zone tied to GVPN — paired with the same inbound NSG/WAF fix already flagged above, since resolving the name alone doesn't yet pass the gate behind it.

Fixes: Scenario 2 end-to-end — but only needed if a WebView/Tab UI is kept; the Adaptive Card path (Scenario 1) already avoids this requirement completely.

Owner: Network / DNS teamEffort: DNS record + 1 rule change
